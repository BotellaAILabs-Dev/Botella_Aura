# Website / CMS blog publishing

Approved blogs publish straight to the customer's own website — no copying and
pasting.

```
Connect website → Create & approve blog → Choose website → Preview → Publish / Draft / Schedule → Track status
```

- **Settings → Website publishing** (`/dashboard/settings/websites`): connect
  sites, see their status, test, reconnect, disconnect, set auto-publish, and
  see the publishing history with Retry.
- **A blog in Content Studio** (`/dashboard/content/:id`): the *Publish to your
  website* panel — pick the site, check the SEO fields, preview, then publish,
  save as a draft on the site, or schedule.

## Platforms

| Platform    | Status                     | Authentication                                                       |
| ----------- | -------------------------- | -------------------------------------------------------------------- |
| WordPress   | **Available**              | Application Password (core WordPress 5.6+), REST API `/wp/v2`        |
| Shopify     | **Available**              | Shopify OAuth (or an existing custom app's Admin API token), GraphQL Admin API |
| Ghost       | **Available**              | Custom integration Admin API key (short-lived JWT per request)       |
| Webflow     | Planned                    | OAuth, Data API v2 (`cms:write`) — needs per-site field mapping       |
| Wix         | Planned                    | OAuth app / API key, Wix Blog draft-posts API (Ricos rich content)   |
| Squarespace | **No API** — not possible  | Squarespace's APIs cover commerce only; there is no blog-post API    |

Squarespace closest option: copy the blog's HTML into a Squarespace Code
block, or use Squarespace's WordPress importer.

### Adding a platform

1. Add it to `lib/website-platforms.ts` (fields, SEO support, limitations).
2. Write `server/websites/adapters/<id>.ts` implementing `WebsiteAdapter`
   (`server/websites/types.ts`): `connect`, `verify`, `listOptions`,
   `findExisting`, `publish`, optional `revoke`.
3. Register it in `server/websites/registry.ts`.

Nothing else changes. Connections, encryption, claiming, retries, duplicate
prevention, scheduling, recurring auto-publish, history, re-auth handling and
the UI are shared. Ghost was added this way, as one file.

## SEO fields

| Field             | WordPress                              | Shopify                                   | Ghost                    |
| ----------------- | -------------------------------------- | ----------------------------------------- | ------------------------ |
| SEO title         | Yoast / Rank Math¹                      | ✅ `global.title_tag` metafield           | ✅ `meta_title`          |
| Meta description  | Yoast / Rank Math¹; always the excerpt | ✅ `global.description_tag` + summary     | ✅ `meta_description`    |
| URL slug          | ✅ `slug`                              | ✅ article handle                         | ✅ `slug`                |
| Canonical URL     | Yoast / Rank Math¹                      | ❌ set by Shopify                         | ✅ `canonical_url`       |
| Focus keyphrase   | Yoast / Rank Math¹                      | ↪ added as a tag                          | ↪ internal tag `#kw`     |
| Open Graph image  | Yoast / Rank Math¹; else featured image | ↪ the article image                       | ✅ `og_image`            |
| Image alt text    | ✅ media `alt_text`                    | ✅ image `altText`                        | ✅ `feature_image_alt`   |
| Schema            | generated by the SEO plugin            | ❌ from the theme                         | ✅ generated by Ghost    |

✅ native · ↪ closest available option · ❌ not possible on that platform

¹ Yoast SEO and Rank Math keep these in post meta, which the WordPress REST
API only accepts if the plugin (or a small snippet) registers those keys with
`show_in_rest`. Aura detects the plugin, sends the fields, **reads the post
back**, and reports which fields the site actually kept. It never assumes they
went through. A site that refuses unknown meta keys gets the post without
them, so the post is not failed over SEO meta.

After each publish, the blog's panel shows *What <site> kept last time*:
`sent`, `closest option`, `not supported` or `empty` per field.

## Content

The blog body is converted to HTML by `lib/blog-html.ts`. The same function
renders the in-app preview, so the preview is exactly what is sent.

- Sections become `<h2>` and their text; `###` sub-headings, paragraphs,
  `-`/`1.` lists, `>` quotes, **bold**, *italic*, `code`, and
  `[links](https://…)` are kept.
- All text is HTML-escaped before markup is applied, so a draft cannot inject
  scripts or tags. Links are kept only for `http(s)`, `mailto:`, `#anchors`
  and site paths. `javascript:` and `data:` are dropped.
- **Internal links**: relative links (`/pricing`) are made absolute against
  the connected site. The publish panel also lists the site's own recent
  posts to add as *Related reading*.
- **Images**: the first attached image is the featured image (with its alt
  text). Further images are placed evenly between sections. WordPress and
  Ghost receive uploads. Shopify fetches the featured image from a
  30-minute signed link and stores inline images in Shopify Files.
- The title is sent as the post title, not repeated in the body.

## Publishing modes

| Choice              | What happens                                                               |
| ------------------- | -------------------------------------------------------------------------- |
| Publish now         | Live on the site immediately.                                              |
| Save as draft       | Created unpublished on the site, for a final look there.                   |
| Schedule for later  | Aura publishes at that time (live or as a draft), in the workspace timezone. |
| Auto-publish        | A recurring slot per site (days + time + how many) takes approved blogs.   |

Scheduling is done by Aura (the `/api/cron/publish` job), not by each
platform's own scheduler. It behaves the same everywhere, can be cancelled in
Aura, and re-checks the approval at the moment it runs. The job must run at
least as often as the precision people expect (see `docs/SCHEDULER.md`); the
default Vercel cron is daily.

### Only approved content

- A blog must be **APPROVED** (or already PUBLISHED) by a person through the
  normal review, and unchanged since (`assertContentIntact`).
- This is checked when publishing is requested and again when a scheduled or
  auto-published run starts. A blog edited after approval fails with
  *"changed after it was approved — approve it again"*.
- Auto-publish only takes `APPROVED` blogs that have never been sent to that
  site, oldest approval first. Turning it on shows *Next up* so people see
  what it will take.

## Status

A blog on each site is one of: **Not connected · Awaiting approval · Ready to
publish · Scheduled · Publishing · Published · Saved as draft · Failed ·
Cancelled**.

A site is one of: **Connected · Connection error · Reconnect required · Not
connected**.

History (`WebsitePublication`, one row per blog per site) keeps the site, blog,
times, status, the actionable error, attempt count, the SEO report and the
last 20 attempts.

## Errors, retries and duplicates

Every failure carries a code and a next step:

| Code        | Meaning                                  | Told to the person                                |
| ----------- | ---------------------------------------- | ------------------------------------------------- |
| auth        | credentials refused / revoked / expired  | Reconnect the site, then Retry                    |
| permission  | the account may not do this              | Change its role on the site, then Retry           |
| validation  | the site rejected a field                | The site's own message; fix it, then Retry        |
| rate_limit  | the site said slow down                  | Retry in a few minutes                            |
| network     | unreachable / timeout / 5xx              | Check the site is online, then Retry              |
| not_found   | a blog/author/post referred to is gone   | Check the site's publishing settings              |

**No duplicate posts:**

1. **One record per (blog, site)**, claimed with a compare-and-swap before the
   site is called. Two clicks, two tabs, or a click racing the scheduler: one
   wins, the other is told it is in progress.
2. **The site's post id is saved the moment the post exists** (an adapter
   checkpoint), even if a later step fails. A retry with an id *updates* that
   post. If it was deleted on the site since, it is created again.
3. **An attempt whose outcome is unknown** (timed out, function stopped) is
   followed by asking the site first (`findExisting`). Shopify articles carry
   an `aura.publication_id` metafield, so they are found for certain.
   WordPress and Ghost match title or slug (including `slug-2`) modified since
   the first attempt.
4. Uploaded images and created categories/tags are remembered per
   publication and reused on retry.
5. The scheduler starts **first attempts only**. A failure or an interrupted
   attempt waits for a person's **Retry**.

**Expired or revoked authentication:** the site becomes *Reconnect required*.
Its owners and admins are emailed once (and messaged on WhatsApp when linked)
on the transition, not per failure. Its scheduled blogs wait rather than
fail, and publish once it is reconnected. Reconnecting the same site keeps its
history.

## Security

- Credentials are AES-256-GCM encrypted (`ENCRYPTION_KEY`) as one blob per
  site and never sent to the browser. Disconnecting wipes them.
- **Disconnect revokes at the platform** where it can: WordPress deletes the
  Application Password itself (via `application-passwords/introspect`), and
  Shopify revokes the OAuth grant. Ghost keys and Shopify custom-app tokens
  are revoked in their own admin. The UI says so.
- **SSRF guard** (`server/websites/safe-fetch.ts`). Site addresses are typed
  by users, so every request:
  - must be https
  - has the address checked when the socket connects, through its DNS lookup,
    which defeats DNS rebinding
  - refuses loopback, private, link-local (incl. 169.254.169.254),
    CGNAT, multicast and reserved ranges, and IPv4-mapped forms of them
  - follows at most 3 redirects, each re-checked, and drops credentials when
    leaving the host
  - is time- and size-limited

  `WEBSITE_ALLOW_PRIVATE_HOSTS=true` allows a local Docker WordPress in
  development only.
- Shopify OAuth: Aura's signed, time-limited `state`, plus a browser-binding
  cookie, plus Shopify's HMAC over the callback query.
- Managing connections needs `company:update`; publishing needs
  `content:publish` (OWNER/ADMIN).

## Setup

**WordPress**: in WordPress go to *Users → Profile → Application Passwords*,
name it "Aura" and create it. In Aura enter the site address (include a
subdirectory if WordPress lives in one), the username and that password. The
user needs the Author role or higher (Editor or higher to create categories).
For SEO-plugin fields, the plugin must expose its meta keys to the REST API.

**Shopify**: set `SHOPIFY_CLIENT_ID` / `SHOPIFY_CLIENT_SECRET` from a Shopify
app with scopes `read_content, write_content, read_files, write_files` and the
redirect URL `<APP_URL>/api/websites/shopify/callback`. People then enter
their `store.myshopify.com` address and approve. Without the app, a store can
paste an Admin API token from an existing custom app with those scopes.
`SHOPIFY_API_VERSION` defaults to `2026-07`; move it forward as Shopify
retires versions. The store needs at least one blog.

**Ghost**: *Settings → Integrations → Add custom integration* → copy the
Admin API key and enter it with the site address.

**Local development**: Shopify fetches images from Aura's signed URLs, so the
app must be reachable from the internet (a tunnel) for Shopify featured
images to work locally. WordPress and Ghost receive image uploads directly.

## Checking against a real site

The unit tests use recorded API responses. Before relying on a platform in
production, run the end-to-end check against a real (ideally staging) site:

```
VERIFY_SITE_PLATFORM=wordpress VERIFY_SITE_URL=https://staging.example.com \
VERIFY_WP_USERNAME=editor VERIFY_WP_APP_PASSWORD="xxxx xxxx xxxx xxxx xxxx xxxx" \
pnpm verify:websites
```

Shopify takes `VERIFY_SHOPIFY_SHOP` and `VERIFY_SHOPIFY_TOKEN`; Ghost takes
`VERIFY_SITE_URL` and `VERIFY_GHOST_ADMIN_KEY`. The script never publishes
anything publicly. It:

1. connects and runs the connection test
2. creates an `[Aura check]` **draft** and prints which SEO fields the site kept
3. confirms an interrupted attempt is found on the site (`findExisting`)
4. confirms a retry updates that same post instead of creating a second one

Delete the draft afterwards; the script prints its id. No database is used.
