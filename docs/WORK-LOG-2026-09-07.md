## 1. Repeating the same work on every navigation — `a64bdc4`

The app was not slow because one thing was slow. It was slow because the **same work ran again on every navigation**, and because two queries grow without limit as the product is used.

**Router Cache.** Every `/dashboard` page is `force-dynamic`, and Next 14 defaults a dynamic segment's client-side Router Cache to **zero**. Re-opening a page you looked at ten seconds ago — or pressing Back — threw away the rendered tree and paid for the session lookup, the company query and the page's own queries again. `staleTimes.dynamic = 30` keeps it. Safe because every mutation in the app already calls `router.refresh()`, which clears that cache outright — verified across all 73 call sites.

**A provider with no readers.** `SessionProvider` was mounted at the root. **Nothing in the app calls `useSession`** — the session is read on the server and passed into the shell as props, and `signIn`/`signOut` do not need the provider. It was costing a `/api/auth/session` request on every page load and another on every window focus, to populate a context nobody read.

**Prefetch on intent.** Dashboard routes are `force-dynamic`, so Next's automatic prefetch only fetches the loading skeleton. Prefetching on hover/focus starts the real render during the ~200 ms before the click. The clicked link now also highlights immediately: `usePathname` only changes once a navigation lands, so the nav previously looked like it had ignored the click.

**Sticky header.** `backdrop-filter` on a `position: sticky` element re-blurs the region behind it on every scroll frame — the usual cause of stuttery scrolling on integrated graphics. The card surface is opaque, so at 80% + blur it already read as solid.

**`listDrafts`.** Content Studio loaded **every draft a workspace had ever produced**, full JSON bodies included, with an implicit select-all — all of it serialised into the RSC payload. Capped at 200 with an explicit column list. The board also sorts by `updatedAt` and no index covered that, so Postgres read and sorted the whole workspace on each load.

Measured against 25,000 seeded drafts:

| Board query | Plan | Time | Buffers |
|---|---|---|---|
| With new index, capped 200 | Index Scan Backward | **0.23 ms** | 41 |
| Without index, capped 200 | Seq Scan + top-N heapsort | 15.0 ms | 4,169 |
| Unbounded (the old code) | full scan, 25,005 rows | 17.1 ms | 4,494 |

**~64× on the query, ~100× fewer buffer reads** — before counting the payload that no longer crosses the wire.

## 3. Dates broke hydration in every non-server locale — `6689fca`

**The most important finding of the day, and nothing in the toolchain caught it.** Not typecheck, not eslint, not all 438 tests, not a 35-route smoke test that reported every page as a clean `200`. It only appeared when a real browser was driven against the app and the console was read.

Every date in the UI was formatted with the runtime's default locale and time zone — `toLocaleDateString(undefined, …)` or a bare `toLocaleString()`. A server-rendered app has **two runtimes, and they do not agree**:

```
Warning: Text content did not match.
  Server: "7 September"            Client: "September 7"
  Server: "7/9/2026, 12:04:44 pm"  Client: "9/7/2026, 2:34:44 AM"
Error: There was an error while hydrating this Suspense boundary.
       Switched to client rendering.
```

React cannot reconcile differing text, so on every affected page it **discarded the server HTML for that whole Suspense boundary and re-rendered it on the client**. That is both a correctness bug — the date visibly changes after load — and a performance one, since the server's work for that subtree is thrown away.

It fires for any user whose browser locale or zone differs from the server's. On Vercel with Indian users, that is all of them. It did not reproduce locally only because the dev machine's Node and Chrome happened to agree.

Two fixes, because these are two different problems:

- **Calendar dates** (a day, not an instant) only need both runtimes to agree. `lib/dates.ts` pins `DATE_LOCALE`, applied at 13 call sites (14 including `LocalTime` itself). `en-US` matches the explicit locale already used in `server/memory/extraction.service.ts`.
- **Timestamps** cannot be fixed that way — the server genuinely cannot know the viewer's time zone. `components/ui/local-time.tsx` renders a pinned UTC string on the server *and on the first client render*, which is what makes hydration match, then re-formats in the viewer's own zone after mount, when React has finished and a change is no longer a mismatch.

**A third bug this surfaced:** the briefing's "Week of …" label read `weekStart` (UTC midnight, from `startOfIsoWeekUTC`) with no `timeZone`, so any viewer behind UTC saw the previous day and the briefing was labelled a week early. Line 366 and `planner-view` already guarded this; that one had been missed.

## Two things I got wrong along the way

Recorded because both would have been reported as real defects if taken at face value.

**A "full page load on every navigation" that wasn't.** A production server on `:3100` appeared to have broken client-side routing entirely — every JS chunk returning 500, React never hydrating. The cause was a `npm run dev` running concurrently on `:3000`: both share `.next`, and the dev build had replaced the production one underneath the running server. Not an app bug. **Only one server can run at a time.**

**A smoke test that reported 10 false failures.** The first error detector matched `digest.*NEXT_`, which appears in Next's flight payload on every page. Rewritten against the actual error-boundary copy in `app/dashboard/error.tsx`.

## What is not done

- **24 other unbounded `findMany` calls** across `server/` share the exact shape `listDrafts` had — fine now, slower every month the product is used. Each needs its own judgement about the right cap, so none were changed.
- **The dashboard home page issues ~8 queries** before it renders anything. The skeleton hides it, but wrapping `SetupChecklist` in Suspense would let the briefing paint without waiting on the checklist.
- **Server components still format dates in the server's time zone.** `lib/dates.ts` makes them deterministic across deploys, but a user in Kolkata still sees UTC-ish dates on server-rendered pages. Fixing that means routing those through `LocalTime` too, which turns several server components into client ones — a real trade-off, not an oversight.
- **The 30 s `staleTimes` window is a judgement call.** It matches the TanStack Query `staleTime` already set in `providers.tsx`. If background jobs start writing data users expect to see sooner, lower it.
